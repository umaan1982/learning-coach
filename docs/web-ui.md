# Local web UI (prototype)

A desktop-only page for using the learning-coach skill at your computer. Not hosted, no API key.

```
webui/
  server/index.js    local HTTP server, bound to 127.0.0.1 (rejects other Host/Origin headers)
  server/claude.js   drives the local Claude Code CLI
  server/scripts.js  runs the skill's Python scripts (no AI)
  server/course.js   turns `course.py status` text into fields (raw text kept as fallback)
  server/plan.js     the Plan tab's data: profile, placement state, `course.py status` + `schedule`, module names
  server/transcribe.py  offline dictation for the mic button (faster-whisper, same model as pronounce.py)
  server/learners.js several learners on one computer: registry + each learner's data folder
  src/components/    our components: Chat, Plan, CTest, Listen, Dashboard, LoginNotice
  src/components/ui/ shadcn/ui primitives (Radix + Tailwind v4, "Nova" preset, Lucide icons)
```

The front end is React (Vite) with [shadcn/ui](https://ui.shadcn.com). The `ui/` files are generated by the shadcn CLI and owned by this repo (add more with `npx shadcn@latest add <name>` in `webui/`). Our own components only compose them. The theme follows the system light/dark setting, and the Geist font is bundled, so nothing loads from the internet at runtime.

## Start

Double-click `start-ui.cmd` in the repo root, or run it from a terminal:

| Command | Data |
|---|---|
| `start-ui.cmd` | your real data, `~/learning-coach-data` (daily use) |
| `start-ui.cmd sandbox` | a throwaway practice folder in the temp dir, for trying things out; your real data is blocked |

If the server crashes, the launcher restarts it after 5 seconds (no new browser tab; it gives up after 5 crashes). Starts, errors, normal stops and crashes are written to `~/learning-coach-profiles/server.log` (no chat text). Closing the console window stops the server on purpose, so keep it open (it starts minimised fine). `LC_NO_OPEN=1` starts without opening a tab.

It installs the packages on first run (and again whenever `package-lock.json` changes, e.g. after a `git pull`), starts the server and opens http://127.0.0.1:5178 in your default browser (any browser works). If the UI is already running, it just opens the page. Close the console window to stop. It runs through `cmd.exe`, so PowerShell's script execution policy doesn't matter.

Developer equivalents: `cd webui`, then `npm run dev` / `npm run dev:sandbox` (or `npm.cmd …` in PowerShell).

## How the backend calls the CLI

One chat turn = one process:

```
claude -p --output-format stream-json --verbose --include-partial-messages
       --permission-mode acceptEdits --permission-prompts none
       --add-dir <skill dir> --append-system-prompt "<where the coach is running>"
       --disallowedTools AskUserQuestion [sandbox: "Read(~/learning-coach-data/**)" Edit(…) Write(…)]
       --allowedTools Skill Read Glob Grep Write Edit "Bash(python *)" "PowerShell(python *)" + read-only ls/cat/cd…
       [--resume <session_id>]
```

There is no one to answer permission prompts in headless mode, so anything not allowed is denied automatically. That is why the allow list covers the scripts (`python …`, through Bash and the Windows PowerShell tool) and a few read-only commands.

- The learner's message goes in on **stdin**, never on the command line.
- The `session_id` from the `system/init` event is kept per data folder and passed back with `--resume`, so a lesson keeps its context. **New session** (asks first) drops it and clears the chat view. Use it for a new day or topic: long conversations get slower and use more of your Claude limits. Nothing is lost, because progress lives in the learner files the coach reads at the start of every session.
- cwd is the learner data folder; `LEARNING_COACH_DATA` is passed through, so the CLI and the panels see the same data.
- The appended prompt names that folder explicitly. Without it the model fell back to the skill's default `~/learning-coach-data`, even on sandbox data. In sandbox mode the deny rules above also block the real folder at the tool level (tested: Read and Glob are refused).
- The data folder is expanded to its long path (Windows reports `%TEMP%` as `C:\Users\JOHNDO~1\…`; Claude Code asks for approval on 8.3 short paths, so edits there were denied).
- **Subscription only:** `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` and leftover `CLAUDE_CODE_*` variables are removed from the child environment. The CLI must be logged in with `claude auth login` (or `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`).
- CLI lookup: `CLAUDE_BIN`, then `PATH`, then `~/.local/bin`, then the copy the Claude desktop app keeps under `%APPDATA%\Claude\claude-code\<version>\`.
- stream-json events are normalised to NDJSON for the browser: text deltas, tool-use lines, audio, and a final `done`. Audio: MP3 file names in `speak.py` output or the coach's text that exist in `<data>/<domain>/audio/` become players in the chat.
- The appended system prompt only covers the setting: the web UI, no clickable-choice buttons, audio shows inline, the C-test is done in the C-test tab (same items, script and scoring; only where you type changes), where the data and scripts are, and to call scripts one at a time (combined shell commands can't be allowed headless). SKILL.md stays the single source of truth for the coaching process. Claude Code records this prompt when a session starts, so changes apply to new sessions only.

## Structured components vs chat

| Interaction | Where | Why |
|---|---|---|
| Lessons, recall, hints, feedback, writing, placement sections B/C | **Chat** | Attempt-first, hint-before-answer and focus-mode messages are the skill's job; the UI only renders Markdown. |
| C-test | **Panel**, `ctest.py make/show/score/result` | An input per gap is far easier than typing `1 ung 2 im …`. The server never sends the answer key; no misses or per-text scores until the end (placement stays neutral); stop early if text 1 < 30% (placement.md). "Hand back to the coach" tells the chat to read `ctest.py result` and continue. |
| Listening audio | **Panel**, `speak.py say` + players inline in chat for the coach's own MP3s | The coach's listening blocks keep the transcript hidden until you've answered (skill rule). |
| Speaking (mic) | **Chat**: mic button → browser recording → `POST /api/recording` → saved to `<data>/<domain>/recordings/` → `transcribe.py` | Works like the Claude app's dictation: the text lands in the input box to check and send. The message is marked 🎤 with the recording's path, so the coach treats it as a spoken answer (e.g. the placement's typed-only rule still applies) and can run `pronounce.py` on it for a pronunciation check. All offline; needs `faster-whisper` (the skill's optional package; ~460 MB model, downloaded once). The browser asks for microphone permission the first time. |
| Plan (guide) | **Panel**: profile, `notes/placement-*.md`, `placement.md` sections, `course.py status` + `schedule`, `course.md` module names | Shows *what's next* (setup → placement → today's lesson) with one button that starts it in the chat, your path, what the placement contains, the current unit and the full week-by-week schedule. The same "next step" is the main button on the chat's start screen. It re-reads after every coach reply. |
| Progress | **Panel**, `dashboard.py` page in an iframe | |

Inputs have spell-check and autocorrect off, so the browser can't give away answers.

**The plan and the exam date.** The schedule is recomputed from `profile.md` (start date, exam date, `unit_weeks`) every time the Plan tab loads and after every coach reply. A later exam date adds spare weeks; the pace stays at one unit per week by design. An earlier date doesn't compress the plan by itself: the Plan tab shows **"Doesn't fit before the exam"** with the options (shorter units in Module 1, testing out of units), and the coach decides with you.

## Several learners (profiles)

Pick who's learning in the header (avatar menu): switch, **Add learner…**, **Rename…**. Each learner has a completely separate data folder, so profile, placement, mistakes, course progress, recordings and chat sessions never mix:

| Learner | Data folder |
|---|---|
| the first one (created automatically, named after your Windows user) | `~/learning-coach-data` (unchanged; also what the Claude app uses) |
| everyone you add | `~/learning-coach-profiles/<name>/` |
| list of learners | `~/learning-coach-profiles/learners.json` |

How it works: the page stores the choice in a cookie, and the server runs every script and every `claude -p` turn with `LEARNING_COACH_DATA` set to that learner's folder (cwd and the session prompt too, which also names the learner). The skill itself is unchanged. **Privacy:** every other learner's folder is blocked for the coach with Read/Edit/Write deny rules, so one person's session can't open the other's files (tested). A new learner starts from the skill's templates (`init_learner.py`) and goes through setup and placement on their own.

Shared between learners: the Claude subscription (and its usage limits), the browser, and Anki. In Anki, give each person their own Anki profile or deck (the coach asks for the deck name during setup). The sandbox has its own separate list of learners.

## Usage limits

Every `claude -p` turn reports the subscription's limits (`rate_limit_event`: utilization per 5-hour and weekly window, reset times; status `allowed`, `allowed_warning` past ~90%, or blocked). The server caches the last value for the login (`learners`-independent, `<profiles>/usage.json`) and `GET /api/usage` serves it, so the header meter shows on page load: "5-hour 92% · resets 01:40 · week 25%", as of the last reply. Amber at ≥80% ("Near your limit: finish this step") with a **Save & pause** button that asks the coach to log the session now; red at ≥95% or when blocked.

From 85% of the 5-hour window, each turn's message starts with a short note *from the UI* asking the coach to save progress to the learner files first (a note on the message rather than the session prompt, because Claude Code records the session prompt once, when a session starts). If a limit stops a turn, the chat says when it resets, puts your message back in the input box with a **Retry** button, and keeps the session id (per learner, in the browser), so you continue the same conversation after the reset. The learner files are always the real record.

## Not logged in

The server checks `claude auth status` before a chat turn (until it succeeds once) and maps the CLI's own "Not logged in" result the same way. Nothing is sent to Claude; the chat shows **Claude CLI not logged in** with the exact command to run once in your own terminal, a Copy button and **Check again**. The message stays in the input box for after login. The UI never runs the login itself.

If `claude` isn't on your PATH, the command uses the desktop app's copy, e.g.

```powershell
& "C:\Users\<you>\AppData\Roaming\Claude\claude-code\<version>\<hash>\claude.exe" auth login
```

That path changes when the desktop app updates the CLI; a standalone install (https://code.claude.com/docs/en/setup) gives a stable `claude` on PATH.

## Status (prototype)

Tested on a sandbox data folder:
- C-test end to end (make → 4 texts → result, stop-early rule, overwrite and blank-gap warnings, "Hand back to the coach"), Listen panel, dashboard, course status, 127.0.0.1-only binding and Host/Origin checks.
- Real chat through the local CLI on the subscription login: the skill loads, replies stream in (~6–25 s per turn), a placement continues across turns with `--resume`, the coach reads/writes only the sandbox files and runs `ctest.py`/`speak.py`, and its audio plays as a player in the chat.
- `start-ui.cmd sandbox`: starts, opens the browser, and a second start reuses the running server.

Not tested: `start-ui.cmd` on a machine without `node_modules` (first-run install), and daily use on real data.
